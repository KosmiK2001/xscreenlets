# sensors

Температуры сенсоров в виде `подпись: число`. Без графиков и истории.

## Источник данных

Читает `/sys/class/hwmon/*/temp*_input` напрямую, без вызова `sensors(1)`.
Причина: conky-конфиги зовут `sensors` через `grep|awk` на каждом кадре,
и его вывод приходится разбирать; в sysfs `tempN_input` — просто целое
число в миллиградусах, разбирать нечего.

## Устойчивость к смене номера hwmon

Номер `hwmonN` — это индекс порядка регистрации драйверов. Он меняется
между загрузками: тот же диск после перезагрузки может оказаться
`hwmon10` вместо `hwmon8`, и строка конфига молча переехала бы на другой
диск.

Поэтому в конфиге лежит не номер hwmon, а **идентификатор строки**
`чип/устройство/канал`:

```
coretemp/coretemp.0/Package id 0
nvme/nvme0/Composite
drivetemp/0:0:2:0/temp1
```

`устройство` — это basename симлинка `hwmonN/device`, то есть имя
конкретного физического устройства. Принцип тот же, что в `disk_monitor`,
где устройство опознаётся по `/dev/disk/by-id`, а не по индексу.

Имя чипа само по себе **не годится**: все четыре nvme называются `nvme`,
все 13 дисков — `drivetemp`. Поиск по имени схлопывает их в один. На этой
машине проверено: 0 дублей идентификаторов из 46 строк.

## Имена в стиле sensors(1)

В Properties сенсоры показываются именами как у `sensors`, чтобы
узнавать их глазами по conky-конфигам. Имена строятся из пути устройства
и сверены с живым выводом `sensors` — совпали все 21.

| класс | пример | как строится |
|---|---|---|
| PCI | `i350bb-pci-0500` | домен и функция отброшены, `05:00` → `0500` |
| NVMe | `nvme-pci-0200` | слот из **последнего** PCI-компонента: `00:02.0` — мост, а не контроллер |
| SCSI | `drivetemp-scsi-0-20` | `host` + `target*10+lun` |
| платформа | `coretemp-isa-0000` | путь `platform/`, слот синтезирован из `coretemp.N` |
| i2c | `nct7904-i2c-1-2d` | адаптер и адрес, ведущие нули убраны |

## Гонка с драйвером BMC

На серверной матери с загруженными драйверами `nct7904` и IPMI сидят на
одном адаптере i2c (на этой машине — `i2c-1`). Параллельное обращение к
драйверу может дать ошибку чтения и запись в dmesg.

Процессов плагин не порождает — только читает файлы, поэтому zombie
невозможен в принципе. Но ошибка чтения обрабатывается явно:
`read_long()` различает три состояния:

- `OK` — значение получено;
- `MISSING` — файла нет (канал не появился);
- `ERROR` — драйвер не отдал значение (конкурентный читатель ipmi).

Канал с ошибкой **остаётся на месте** и показывается как `—`. Иначе сбой
одного чтения убирал бы строку на кадр, и она мигала бы. Нулевое
значение при ошибке не подставляется: «0.0°C» среди настоящих каналов
неотличим от измерения.

Значение `-128000` (маркер «сенсор не подключён») тоже показывается как
`—`, а не как минус 128 градусов.

## Настройки

Properties показывает все найденные сенсоры с галочками; выводятся только
отмеченные. Галочки меняют и порядок строк, и состав — порядок задаёт
пользователь, а не алгоритм.

Остальные ключи — в `config-examples/sensors.conf.example`.

## Известные грабли

- **Кегль в единицах PANGO_SCALE.** `pango_font_description_get_size()`
  для `Sans 8` возвращает 8192, а не 8. Подстановка числа в описание
  шрифта даёт `Sans 8192`: окно рисует рамку, а текст не появляется
  вообще. Делить на `PANGO_SCALE` обязательно.
- **Ключи init и обработчиков должны совпадать.** Расхождение
  невидимо: файл меняется, а на экране ничего.
- **В rows пишется пара `подпись|источник`.** Запись одних подписей
  теряла привязку к устройству, и строка переживала бы перезагрузку
  только до первого сохранения — а оно происходит в init.
