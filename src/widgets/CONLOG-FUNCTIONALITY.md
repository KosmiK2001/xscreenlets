# conlog — что убрано из апплета и как вернуть

Документ к `conlog_min.c`. Апплет намеренно урезан: он показывает
только текст. Всё, что было сверх этого, описано здесь — с цифрами
замеров и с порядком возврата.

`conlog.c` и `conlog_core.c` остались на месте нетронутыми, тесты
`tests/test_conlog.c` (417 проверок) продолжают их собирать и проверять.
Урезанная версия собирается отдельно: `make build/conlog_min.so`,
устанавливается как `lib/xscreenlets/plugins/conlog.so`.

## Главный вывод замеров

Поведение applet'а на большом выводе объясняется не алгоритмом, а
объёмом данных. Замер на команде

```sh
cat -A /dev/urandom | grep -e '[a-z|A-Z|0-9]'
```

это примерно 290 000 строк/с:

| величина | значение |
|---|---|
| CPU демона | **90.6%** — почти целое ядро |
| состояние главного потока | постоянно `R` |
| обновление applet-а | раз в несколько секунд |
| чтение | 11 280 `read`/с по ~3967 байт |
| поток через applet | 40 МБ/с |
| стоимость | 23 мс процессорного времени на 1 МБ |

Стоимость линейна:

| поток | CPU |
|---|---|
| 0.004 МБ/с | 0.01% |
| 0.04 МБ/с | 0.09% |
| 0.4 МБ/с | 0.91% |
| 40 МБ/с | 91% |

Демон при этом не падал, но и не справлялся: `pkill -9` его не брал,
процесс уходил в зомби — applet намертво залипал на чтении из pipe.

**Вывод: оптимизация разбора это не чинит.** Даже идеальный разбор
остаётся узким местом на 40 МБ/с. Нужен предел приёма, и именно он
поставлен в `conlog_min.c` двумя константами:

```c
#define CONLOG_MAX_LINES        200        /* сколько строк хранить */
#define CONLOG_MAX_READ_BYTES   (64 * 1024) /* предел на один вызов */
```

`CONLOG_MAX_LINES` ограничивает только хранение: лишние строки всё
равно приходится прочитать. `CONLOG_MAX_READ_BYTES` ограничивает
прочитанные байты за один вызов обработчика — после него applet
возвращается в main loop, и сколько бы данных ни лежало в pipe, уйти
в бесконечный разбор он не может.

## Что убрано

| было | где было | цена |
|---|---|---|
| разбор SGR-последовательностей | `conlog_core.c` | дорого, но кэшировалось по `conlog_seq` |
| кэш разбивки на прогоны | `conlog.c`, `cl_runcache_*` | ~9% CPU на `ls --color` без кэша |
| подсветка по уровню сообщения | `conlog_level_color`, 5 цветов | поиск по словарю на строку |
| перенос длинных строк | `wrap` | мерка каждой строки через Pango |
| авторазмер окна по содержимому | `width_auto`, `height_auto` | `conlog_text_width` на каждой строке |
| прокрутка колесом мыши | `cl_scroll_cb` | обработка события |
| экран настроек | `cl_properties`, ~600 строк | не влияет на CPU, но это объём кода |
| SGR-кэш прогонов | `cl_rebuild_cache` | сбрасывался при смене шрифта |
| своя отрисовка в поверхность | `cl_rebuild_cache` | кэш поверхности applet-а |

Ключи конфига, которые перестали читаться: `colorize`, `wrap`,
`strip_ansi`, `keep_ansi`, `autoscroll`, `width_auto`, `height_auto`,
`corner_radius`, `opacity`, `cwd`, `color_normal`, `color_warn`,
`color_error`, `color_info`, `color_debug`, `title_dx`, `title_dy`.

## Что осталось

- запуск команды через `GSubprocess` + `/bin/sh -c`;
- неблокирующее чтение stdout через `GIOChannel`;
- свой буфер строк (`GPtrArray`, `GString` для недописанной строки);
- предел приёма (см. выше);
- отрисовка по таймеру `CONLOG_REDRAW_MS = 100` мс;
- метка, разделитель, цвет текста, фона, рамки, `max_lines`,
  `line_step`, `first_row_y`, `row_font`, `title_font`, `x`, `y`.

`invalidate()` раньше звался на каждое чтение: при потоке это сотни
вызовов в секунду на пустом деле, потому что видны только 200 строк.
Теперь перерисовка ограничена 10 Гц.

## Ошибки, найденные при переходе

Их было четыре, все в новом файле. Записаны, потому что при возврате
функциональности те же грабли ждут.

1. **`p->win` обязан создать плагин.** Демон после `init` проверяет
   `p->win != NULL` и без окна пишет `init failed` и выгружает
   инстанс. Нужны также `xs_host_api()->set_opacity()` и `set_tick()`.
2. **`double free` в буфере строк.** У `GPtrArray` задан
   `free func = g_free`, поэтому `g_ptr_array_remove_index()`
   освобождает элемент сам. Свой `g_free()` перед ним даёт
   «double free or corruption» на первом же вытеснении старой строки.
3. **Геометрия шапки.** Метка рисуется в зоне
   `[first_row_y, first_row_y + title_h)`, разделитель — под ней,
   строки — ниже разделителя с просветом `CONLOG_ROWS_GAP`. Если начать
   строки с `y = MARGIN`, а метку рисовать на `y = MARGIN / 2`, они
   наезжают друг на друга: визуально это выглядит как «текст слипся».
4. **Утечка `PangoFontDescription`.** `cl_font()` возвращает новый
   дескриптор; отдавать его прямо в `pango_layout_set_font_description()`
   нельзя, он утекает на каждом кадре.

### 5. Утечка таймеров (обязательно прочитать, если будешь править отрисовку)

Самая дорогая ошибка, которую я здесь сделал, и она не выглядит как
ошибка.

`cl_redraw_cb()` возвращала `G_SOURCE_CONTINUE` — то есть таймер
продолжал жить, — но при этом обнуляла `priv->redraw_id`. Таймер
отрисовки «взводился заново» в `cl_schedule_redraw()`, которую звал
`cl_on_io()`: источник оставался в очереди, `redraw_id` становился 0,
следующее чтение добавляло ЕЩЁ ОДИН источник. При 19 строках/с через
минуту накапливались сотни таймеров, и каждый дёргал `invalidate()`
с частотой 10 Гц — десятки тысяч перерисовок в секунду.

Симптом снаружи выглядел не как баг отрисовки, а как «демон ест 30–45%
CPU». На живом `journalctl -f -n 15`:

| состояние | CPU демона |
|---|---|
| с утечкой таймеров | 30–45% |
| conlog отключён | 6.1% |
| после исправления | 7.2–7.3% |

Правило: у источника, который живёт всё время жизни applet-а, должен
быть ровно один id, и снимать его надо в `shutdown`, а не в `stop`.
`cl_stop()` вызывается ещё и из `cl_start()` при перезапуске команды —
если снимать таймер там, он умрёт при первом же перезапуске. В ветке
отказа `cl_init()` (не создалось окно) таймер снимается ДО `g_free(priv)`,
иначе он через секунду бьётся по освобождённой памяти.

Проверка на утечку — два замера подряд с интервалом в минуту: если
второй выше первого, таймеры копятся.

## Настройки

Экран Properties возвращён — без него applet нельзя настроить, а
править конфиг руками неудобно. Вкладка **Command**:

| ключ | что делает |
|---|---|
| `command` | команда через `/bin/sh -c`; при изменении процесс перезапускается сразу |
| `refresh_interval` | сек; 0 = запуск один раз (историческое поведение), N = перезапускать команду каждые N секунд («режим conky», см. PLAN-CONLOG-REFRESH.md) |
| `title` | надпись; пусто — не рисуется вместе с разделителем |
| `max_lines` | сколько строк хранить |
| `line_step` | высота строки, 0 = по шрифту |
| `first_row_y` | отступ до зоны заголовка |
| `row_font` / `title_font` | шрифты |
| `row_color` / `background_color` / `title_color` | цвета |
| `window_width` / `window_height` | размер окна |

Записи `cl_entry_changed` / `cl_spin_changed` / `cl_color_set` /
`cl_font_set` пишут в `priv->kf` и вызывают `xs_core_plugin_conf_flush()`.

Две вещи, которые легко забыть при возврате настроек:

- `cl_props_group()` — обёртка, добавляющая страницу в `GtkNotebook` с
  описанием сверху. Хелперы `xs_prop_add_*` принимают `GtkBox *`, а
  `gtk_box_new()` возвращает `GtkWidget *`, поэтому нужен явный
  `GTK_BOX(page)`.
- `cl_start()` из обработчика `command` обязателен: иначе в окне навсегда
  останется вывод предыдущей команды, пока applet не перезапустят.

### 6. SIGSEGV при смене команды в Properties (самое дорогое по последствиям)

Ввод команды в Properties ронял демон мгновенно. Воспроизводится
только через GUI: та же команда, прописанная в конфиг руками, работает
без единого падения — потому что при ручной правке applet стартует один
раз, а из GUI он стартует второй раз поверх уже работающего.

Причина в том, что `g_subprocess_get_stdin_pipe()` и
`g_subprocess_get_stdout_pipe()` возвращают **borrowed**-ссылку
(в `gsubprocess.h` у них нет `(transfer full)`), а я unref-ил их в
`cl_stop()`. Падало уже в следующей итерации main loop, когда
отрабатывал child-watch:

```
#0  g_type_check_instance_is_fundamentally_a ()
#1  g_object_unref ()
#2  ??? () from libgio-2.0.so.0     <- async finalize потока
#3  g_object_unref ()                <- g_main_context_iteration
```

Правила владения, которые здесь действуют:

| объект | кто владеет | что можно |
|---|---|---|
| `GSubprocess` от `g_subprocess_newv()` | мы (transfer full) | unref обязателен, иначе течёт на каждом перезапуске |
| stdin/stdout из `g_subprocess_get_*_pipe()` | `GSubprocess` (borrowed) | **unref нельзя**, только использовать |
| `GIOChannel` от `g_io_channel_unix_new()` | мы | unref, и дескриптор ему свой |

Рабочая схема: `dup(fd)` для канала, `g_io_channel_set_close_on_unref()`,
наши ссылки на потоки не unref-ятся, `GSubprocess` unref-ится в
`cl_stop()` после `g_subprocess_force_exit()`.

Порядок в `cl_stop()` тоже важен: сначала `g_source_remove(watch_id)`,
затем `g_io_channel_shutdown()`, и только потом освобождение процесса —
пока источник жив, канал держит ссылку.

Как ловить: падение происходит не в момент правки, а на следующей
итерации main loop, поэтому в crash-логе и логе демона может не быть
ничего. Проверять надо exit code (`139` = SIGSEGV) и `g_object_unref` в
трейсе.

### 7. Цвета не переживали рестарт

Здесь было три ошибки подряд, и первые две маскировали третью.

**Первая: несовпадение форматов записи и чтения.** Писалось
`"%g,%g,%g,%g"` (дробные 0..1), читалось `sscanf("rgba(%d,%d,%d,%d)")`
(целые 0..255) — значение не распознавалось, `cl_rgba()` тихо
возвращала дефолт. Запись переведена на `rgba(r,g,b,alpha)`, как в
оригинальном `conlog.c`.

**Вторая: `%.3f` в alpha.** У демона `LC_ALL=ru_RU.UTF-8`, где
десятичный разделитель — запятая, и `printf("%.3f", 1.0)` печатает
`1,000`. Такое значение сохранялось как есть, и при чтении получалось
`rgba(0,255,0,1,000)` — пять компонент вместо четырёх. Alpha теперь
пишется целым числом байт, как r/g/b.

**Третья, настоящая: `sscanf` с плавающей точкой ломается о локаль.**
Переведя чтение на `%lf` ради дробного alpha, я сломал его снова:
в `ru_RU` `sscanf("%lf")` ждёт запятую как десятичный разделитель,
поэтому на строке `rgba(255,0,0,255)` разбор возвращал 2 из 4 и цвет
снова уходил в дефолт. Проверено отдельно:

```
rgba(255,0,0,255)  в ru_RU: n=2    в C: n=4
```

При этом `sscanf("%d")` в `ru_RU` работает (он целочисленный, локаль
не при чтении целых не участвует), а вот `%ld` — нет. То есть
`printf`/`sscanf` с плавающей точкой в русской локали непригодны без
явного переключения.

Решение: `rgba()` разбирается руками, цифры и запятые — `cl_u32_after()`.
От локали не зависит ничего. Старый формат `r,g,b,a` от `conlog_core`
разбирается через `strtod`, но с временным `setlocale(LC_NUMERIC, "C")`
и с проверкой диапазона 0..1: в старых конфигах есть шестикомпонентный
мусор `0,870588,0,866667,0,854902,1`, где первые четыре — не
компоненты цвета, и без проверки получалось `g=870588`.

Мелочь в самом разборе: `cl_u32_after()` останавливается на первой
не-цифре и саму её не съедает, поэтому после каждого числа запятую
нужно пропускать явно (`*p++ == ','`). Без этого цепочка
условий рвалась на первом же разделителе.

**Проверка.** Парсер надо прогонять под `LC_ALL=ru_RU.UTF-8` — под `C`
он работает и со сломанным кодом, и все тесты проходят зелёными. Это
и было причиной того, что правка «выглядела» сделанной, а эффекта не
давала.

### 8. Ревью GLM-5.3-flash: что нашлось и что оказалось неверным

Ревьюёр нашёл две вещи, которые бьют в цель переписки, и несколько мелких.

**`set_buffered(TRUE)` убивал смысл `CONLOG_READ_CHUNK`.** При включённой
буферизации GLib читает во внутренний буфер размером
`G_IO_NICE_BUF_SIZE` = **1024 байта**, сколько бы мы ни просили. То
есть read() шёл тысячебайтными кусками, и замысел «крупный кусок =
16K» не выполнялся вовсе. Замерено на чтении 256 КиБ:

| режим | вызовов read() |
|---|---|
| `set_buffered(TRUE)` (было) | **268** |
| `set_buffered(FALSE)` (стало) | **28** |

Ровно та же гранулярность, что была в старой версии. Буферизация
выключена, `read()` идёт прямо в наш буфер полным `CONLOG_READ_CHUNK`.

**`make install` ставит тяжёлую версию.** Цель `install` копирует
`build/conlog.so` (оригинальный conlog.c + conlog_core) как
`plugins/conlog.so` и молча откатит урезанный applet вместе с его
90% CPU. Ловушка помечена комментарием в Makefile, сам applet ставится
вручную: `cp build/conlog_min.so ~/lib/xscreenlets/plugins/conlog.so`.

Мелочи, исправленные по ревью:

- `cl_font_set()` не освобождал `fname` — `gtk_font_chooser_get_font()`
  отдаёт transfer full, строка была утечкой на каждый выбор шрифта.
- `cl_init()` оборачивал результат `conf_str()` в `g_strdup()`, а
  `conf_str()` уже возвращает свежую копию — четыре утечки на каждый
  init/recreate.
- После ветки HUP `priv->watch_id` не обнулялся, и следующий
  `cl_stop()` дёргал `g_source_remove()` по мёртвому id (g_warning).
- Ранние выходы `cl_start()` оставляли запущенный процесс без читателя:
  без `dup` ребёнок упёрся бы в заполненный pipe и завис. Добавлен
  `g_subprocess_force_exit()`.
- Значения `window_width/height`, `line_step`, `first_row_y` клампились
  только в Properties, а в конфиг писалось сырое значение спиннера.
  Теперь клампится и при чтении.

**Что ревьюёр ошибся.** Он поставил под сомнение замер в разделе 7:
«`sscanf("%lf")` разбирает целые без разделителя в любой локали, в ru_RU
n должен быть 4». Это не так — замер воспроизводится:

```
sscanf("rgba(255,0,0,255)", "rgba(%lf,%lf,%lf,%lf)")
  ru_RU.UTF-8 -> n=2        C -> n=4
```

Проверено повторно отдельной программой. Также неверно утверждение
«`%ld` в ru_RU не работает». Суть проблемы реальна и решение верное,
просто обоснование в ревью было неверным.

## Порядок возврата функциональности

Если понадобится, по одному пункту за раз, с замером после каждого.

### 1. Подсветка по уровню (самая дешёвая)

Возвращается без conlog_core: на готовой строке ищутся слова словаря,
выбирается цвет из массива. `conlog_level_color()` в оригинале делает
ровно это. Стоимость — поиск по границам слова на 200 видимых строках,
то есть на порядок дешевле разбора SGR.

Ключи: `colorize` и пять цветов уровней.

### 2. Прокрутка колесом

`g_signal_connect(p->win, "scroll-event", ...)` и сдвиг
`priv->scroll_top`. `scroll_top` в урезанной версии уже есть, рисуется
используется — поле живое, осталось только повесить сигнал. При
`autoscroll` хвост всегда показывается.

### 3. Перенос длинных строк

`wrap=1` меряет каждую строку через Pango и делит. Дорого: мерка
идёт по всем строкам буфера, а не только по видимым, если мерка
делается при добавлении. Считать при добавлении — тогда цена
одинарная на строку.

### 4. Авторазмер окна

`width_auto` / `height_auto`: окно подстраивается под самое длинное
слов и по число строк. Мерка — только для вновь добавленных строк,
плюс один пересчёт по всему буферу при смене шрифта.

### 5. Цвета вывода SGR (самое дорогое)

`keep_ansi=1` разбирает escape-последовательности, режет строку на
прогоны и красит каждый своим цветом. В оригинале разбивка
кэшировалась по порядковому номеру строки, и кэш сбрасывался при
смене шрифта и перезапуске команды — без этого демон уходил в 99% CPU
на `ls --color`. Возвращать только вместе с кэшем.

## Проверка стендом

`temps/conlog-feeder.py` — бесконечная подача строк с точным темпом
(файл перечитывается по кругу, так что «большой вывод» не кончается):

```sh
python3 temps/conlog-feeder.py temps/conlog-bench-1m.txt 300 0
#                                                    │   └ 0 = бесконечно
#                                                    └ мс между строками
```

Файл — 12 356 строк, 1 МБ, только печатные символы, без переносов
внутри строки. Таймер отсчитывает интервал от начала цикла, поэтому
средняя скорость не плывёт: проверено 20.0 строк/с при цели 20.0.

Для предельной нагрузки стенд не нужен — `cat -A /dev/urandom | grep`
даёт поток, который applet заведомо не переварит.

## Чего applet принципиально не сможет

Поток в десятки мегабайт в секунду. Даже с пределом приёма applet
прочитает 64 КиБ за вызов, но источник продолжит писать в pipe, и
команда (`cat` без ограничения) будет расти, пока не упрётся в
буфер ядра. Если источник бесконечный и быстрый, разумно ограничивать
его на стороне команды:

```ini
command=dmesg --follow | head -c 100000
```
