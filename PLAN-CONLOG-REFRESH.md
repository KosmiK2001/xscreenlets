# PLAN: conlog — надёжный вывод «по таймеру» (вариант «как conky»)

Статус: РЕАЛИЗОВАНО в conlog_min.c (2026-10-10). Ключ refresh_interval,
групповой kill через child_setup+setpgid, таймер перезапуска. Гейт:
make clean && make = 0 ошибок/предупреждений, все тесты зелёные
(417 conlog + 258 conlog_core + прочие), стенд: refresh=2 -> 8 запусков
за окно, хвосты не копятся, после ротации tail держит НОВЫЙ inode;
refresh=0 -> ровно 1 запуск (regression цел).
Контекст: `conlog_min.c` — текущий развёрнутый апплет (в гите лежат оба:
`conlog.c`/`conlog_core.c` — полный эталон с тестами, и `conlog_min.c` —
работающий; ebuild ставит `conlog_min.so` под именем `conlog.so`,
полный вариант игнорирует).

## Симптом и диагноз (проверено на живом сервере)

Апплет показывает вывод, но «со временем зависает». Найдено у инстанса
`named_log` (команда `tail -n 24 -f /var/log/named/queries.log | grep ... | awk`):

- Ротация лога 10 окт 03:05: `queries.log` стал inode 7 (новый, растёт),
  старый inode 6 уехал в `queries.log.0`.
- `tail -f` (lowercase) следует за **дескриптором**, ротацию не переносит.
  У живого процесса: `/proc/<tail>/fd/3 -> /var/log/named/queries.log.0`
  (старый inode). Пипе с тех пор пуст — фид закончился ещё в 03:05.
  Спасает только `tail -F` (на capital) или переоткрытие файла заново.
- Второй инстанс `dmesg` (`cat ... | tail -n 30 | awk`) — команда ОДНОРАЗОВАЯ:
  печатает 30 строк и завершается; его «зависание» — это просто команда
  уже отработала.
- В системе три осиротевших старых `tail -f` (ppid 1, 3 дня) — от прошлых
  попыток, тот же неверный паттерн; не трогать без согласия.

Конструктивный пробел `conlog_min`: при HUP/смерти команды watch снимается
и команда НИКОГДА не перезапускается — любой обрыв фида застывает до
ручного рестарта апплета.

## Варианты (записаны, чтобы не потерять)

1. **Команда как есть + авторестарт на HUP в conlog_min.** Ветка G_IO_HUP
   после съёма таймера/канала вызывает `cl_start()` снова; нужна защита от
   шторма рестартов для быстропадающих команд (backoff). Минус: текущий
   фриз от ротации НЕ лечит — `tail -f` снова встанет на старый inode.
2. **Только команда: `-f` → `-F`** в конфиге named_log. Закрывает текущий
   фриз у одного инстанса; плагин остаётся беззащитным к смерти команды.
3. **== ВЫБРАН ==: периодический перезапуск команды «как conky».**
   Команда запускается по таймеру `refresh_interval` (сек, 0 = выкл).
   Каждый запуск — свежее переоткрытие источников, ротация несущественна,
   смерть команды самоизлечивается следующим тиком. Субсумирует вариант 1.

## Дизайн выбранного варианта (черновик)

Новый ключ конфига `refresh_interval` (целые секунды, 0 = выкл = текущее
поведение). Свойства: спиннер «Refresh interval, s» (0..3600, шаг 1).

Семантика при > 0:
- Раз в `refresh_interval` секунд: `cl_stop()` (форс-выход текущей команды) →
  очистка `lines` + `pending` → `cl_start()` заново.
- Вывод нового запуска ЗАМЕНЯЕТ содержимое окна (семантика conky).
- «Разумный потолок» каждого запуска — следующий тик: `-f`-команда будет
  прибита на границе интервала, что она успела выдать — показано.
  Отдельный лимит времени запуска не нужен.
- Для этого режима команду писать БЕЗ `-f`/`-F`: `tail -n 24 файл` — свежий
  снимок на каждый тик, ротация неважна вовсе.
- При 0 — ровно сегодняшнее поведение (один запуск, чтение до HUP);
  инстанс dmesg остаётся одноразовым, всё обратно совместимо.

Таймер: ОДИН источник на время жизни апплета (как `redraw_id`), создаётся в
`cl_init` если `refresh_interval>0`, снимается в `cl_shutdown`, НЕ в
`cl_stop`/`cl_start` (они вызываются на каждый тик). При смене значения в
Properties — пересоздать источник. В колбэке проверка живучести priv
(`if (!priv) return G_SOURCE_REMOVE`).

CPU: цена ограничена — каждый запуск читает ≤ CONLOG_MAX_READ_BYTES за
вызов обработчика, перерисовка 10 Гц только по dirty-флагу; `tail -n N`
стоит миллисекунды на интервал. Шторм рестартов невозможен: период задаёт
пользователь, даже 1 с с мгновенной командой — копейки.

КЛЮЧЕВОЕ ТРЕБОВАНИЕ — убивать ВЕСЬ процесс-группу, а не только shell.
`g_subprocess_force_exit()` посылает SIGTERM только `/bin/sh -c`; `tail`
и `awk` остаются сиротами, а `tail -f` на живом/переименованном файле
не пишет → не рвётся по SIGPIPE — остаётся НАВСЕГДА. Осиротевшие
`tail` (529482, 530387, 532236, ppid 1) — это старые демоны-перезапуски,
которые убивали shell, не трогая пип. В периодическом режиме без
process-group kill такие сироты плодились бы НА КАЖДЫЙ тик.
Решение: `g_subprocess_launcher_set_child_setup()` + в child-setup
`setpgid(0,0)` перед exec; pid группы = `g_subprocess_get_pid()`; при
`cl_stop()` — `kill(-pid, SIGTERM)` и после короткой паузы SIGKILL, либо
сразу SIGKILL (вывод запуска всё равно выбрасывается). Это требование
включено в реализацию.

Открытые вопросы:
- Единицы: секунды (как `update_interval` у conky) против мс. Секунды.
- Порядок/потеря хвоста: если на границе тика прошлый запуск ещё шёл,
  `cl_stop` рвёт канал — теряются последние миллисекунды вывода; приемлемо
  (ограничено интервалом).
- Мёртвые дети шелл-a решаются SIGKILL группе, см. требование выше.

## Порядок доставки (обязательно)

1. Реализация в `conlog_min.c` + ключ в PROPERTIES + конфиг-пример.
2. `make` — 0 ошибок/предупреждений (Russian locale: «ошибка» тоже маркер);
   `make build/conlog_min.so` отдельно; `make test`.
3. Проба на изолированном стенде (feed `temps/conlog-feeder.py` +
   `tail -n 24 file`, ротация файла на лету — проверить, что снимок свежий).
4. Проставить `refresh_interval` инстансу named_log (команду упростить:
   `tail -n 24 /var/log/named/queries.log | grep --line-buffer -v ... | awk ...`).
5. `git push` → `emerge --sync kosmik2001` → `emerge --unmerge xscreenlets`
   → `emerge xscreenlets` (всё через `sudo -n`), проверка установленного
   `conlog.so` (`strings | grep 2.0-min`).
